# 2026-10-21 鸿蒙签名接入

## 任务
用 DevEco/AGC 生成的签名材料给本项目的鸿蒙 app 签名；确认是否支持鸿蒙 desktop。

## 签名材料的事实
- `~/Documents/hiddify.p12` + `hiddify.csr`（08:14 生成）= **能用的那一对**，
  私钥 EC P-256，库内证书是自签名的 `CN=hiddify-app`。
- `ohos/secrets/regenerated-20261021-1032/`（10:32 重新生成）= **另一把私钥**，
  AGC 没签它，原密码也打不开，已原样保留。
- AGC 下载的 `Hiddify-app.cer`（11:04）= 华为 CBG 签发的**正式 Release 证书链**：
  叶子 `CN=党航飞(2065945048494666753)\,Release` → `Huawei CBG Developer Relations CA G2`
  → `Huawei CBG Root CA G2`。**叶子公钥与 08:14 那把 p12 匹配**（指纹 fe49493556dd1e35）。
- `agconnect-services.json` **不是签名材料**，是 AGC 运行时服务配置（端点 + client_secret
  + api_key + code1..4），含机密，别进仓库。

## 踩坑
1. **hap-sign-tool 的 `sign-app` 要求 `-appCertFile` 是证书链**（≥2 张），且链根要有
   CA 属性的 basicConstraints。库里那张自签名单证书两条都不满足，直接报
   `11013004 Profile cert must a cert chain`。解法：用**同一把私钥**再签一张本地根 CA
   （CA:true）+ 一张应用证书（codeSignature），链 = 应用证书 + 根 CA。私钥不变，CSR 依然匹配。
2. **`sign-profile` 另需三级链**（叶子+子CA+根CA），所以 Profile CA 链单独放
   `secrets/profile-ks.p12`。
3. **`sign-profile`/`sign-app` 不校验 p7b 里的 development-certificate 与 app 证书是否一致**，
   签名阶段会过，但真机安装时会因「签名证书与 profile 不匹配」拒装。
4. **AGC 证书链的顺序**：AGC 下载的是 根→中间→叶子，`certpath` 要求**叶子在前**，要重排。
5. **hvigor 的 material 目录位置** = `<storeFile 所在目录>/material`（DecipherUtil.getKey），
   且 `fd/` 下必须正好 3 个子目录、每个 1 个 16 字节文件，`ac/`、`ce/` 各 1 个文件。
   口令密文 = [BE32(ivLen+ctLen+4)][iv][ct][tag]，key 由
   PBKDF2(xor(fd0^fd1^fd2^component), salt, 10000, 16, sha256) 派生，
   component = [49,243,9,115,214,175,91,184,211,190,177,88,101,131,192,119]。
6. **`type` 字段只在 compileSdkVersion ≤ 8 时才校验**（Hapv2SignCommandBuilder），
   API 26 走 HapSignCommandBuilder，不校验。
7. `flutter build app` 只把 `ohos-default-signed.app` 拷到 `build/ohos/app/`；
   `ohos-default-all-signed.app`（内嵌 hap 也签名）要手动从
   `ohos/build/outputs/default/` 拷过去。

## 产出（ohos/signature/，已提交）
- `sign-with-keystore.sh` —— 用 secrets/ 下的 p12 重签根 CA + 应用证书 + Profile CA 链，
  签 p7b，派生加密口令，写 build-profile.json5。口令从 `KEYSTORE_PASSWORD` 环境变量读。
- `derive-store-password.js` —— 复用已有 material 目录派生 storePassword 密文 hex。
- `use-signing.sh <default|local-debug>` —— 切换 product 用的签名配置。
- 原来那套自签材料（`ohos/signature/` 下的 app-cert.cer / hiddify-debug.p7b /
  material/ / generate-debug-signature.sh / generate-signing-material.js）已被
  `sign-with-keystore.sh` 取代并删除；文档落在 `docs/harmonyos.md`。

## 配置
`ohos/build-profile.json5` 有两套 signingConfigs：
- `default` —— AGC 正式签名：certpath=`secrets/hiddify-app-agc.cer`，
  profile=`secrets/hiddify-app-agc.p7b`（**该文件目前还没有**）
- `local-debug` —— 本地自签：certpath=`secrets/hiddify-app.cer`，profile=`secrets/hiddify-app.p7b`

## 遗留
- **缺 AGC 的 `.p7b`**：AGC 同一个「下载证书」包里应该还有 `Hiddify-app.p7b`，
  放到 `ohos/secrets/hiddify-app-agc.p7b` 即可。拿到前 `default` 构建会报
  `00303107 Configuration Error`；用 `use-signing.sh local-debug` 可继续出包（仅 OpenHarmony 设备/模拟器）。
- 真机安装还需要 profile 与设备 UDID 匹配（debug profile 要在 AGC 登记设备）。

## 鸿蒙 desktop 结论
- **工具链支持**：Flutter OHOS SDK 有 `ohos-x64` 目标（鸿蒙 PC 是 x86_64），
  实测 `flutter build hap --target-platform ohos-x64` 出包成功；hvigor `DeviceTypeConst`
  有 `pc`/`2in1`；HarmonyOS API 26 的 module.json schema 允许 deviceTypes 含 `2in1`。
- **本项目未配置**：`ohos/entry/src/main/module.json5` 的 deviceTypes 只有 `["phone"]`。
- **真正的拦路虎（与形态无关）**：`hiddify-core` 没有 OHOS 原生库（Makefile 只有
  desktop/mobile 目标），hap 里只有 libapp.so/libflutter.so；`getCoreInterface()` 判断
  `Platform.isAndroid || Platform.isIOS`，OHOS 上都 false，于是落到
  `CoreInterfaceDesktop` 去 `DynamicLibrary.open("hiddify-core.so")` → 运行时抛异常。
  **当前手机形态的鸿蒙版代理功能也不可用**，不是 desktop 独有。
  要做桌面/真机可用，得先给 core 出 OHOS 的 arm64/x86_64 构建，并给
  `core_interface_wrapper.dart` 加 ohos 分支。

## 鸿蒙权限（module.json5 requestPermissions）
- **必须走 AGC ACL 审批的只有 1 项**：`ohos.permission.GET_NETWORK_STATS`
  （system_basic / system_grant）。华为《受限开放权限列表》里明确把
  「VPN 类应用，用于查询相关流量消耗」列为合规场景，审核约 3 个工作日。
  变更说明：从 API 26.0.0 起才开放给普通应用（API 10-24 仅系统应用）。
- `ohos.permission.MANAGE_VPN`（system_basic）**不在**受限开放权限列表里，
  不用单独申请 ACL，但要在 profile 里带上。配套要加
  `extensionAbilities: [{ type: "vpn", srcEntry: ... }]`（API 26 的枚举值是
  `vpn`，老资料的 `vpn.extension` 已不合法）。
- profile JSON 里 `acls.allowed-acls` 放受限 ACL，`permissions.restricted-permissions`
  放 user_grant（运行时弹窗），两者不是一回事。
- `reason` / `usedScene` 只有 user_grant / manual_settings 权限必填；
  `reason` 走 `$string:` 资源引用，要多语种（base/en_US/zh_CN）。
- 参考：SDK 的 `openharmony/toolchains/lib/PermissionDefinitions.json`
  （每个权限的 grantMode / availableLevel / availableType / provisionEnable）
  和 `UnsgnedDebugProfileTemplate.json`（profile 的 acls 字段长什么样）。

## ohos 插件接入（pubspec）
社区把 ohos 实现单独发成 `<plugin>_ohos` 包，发布在 pub.flutter-io.cn 镜像上
（也有 gitee `openharmony-sig/fluttertpc_*` 和 github `harmonycandies/*_ohos` 的源码）。
两种接入方式：
- **federated**（`implements: xxx`）：path_provider / shared_preferences / url_launcher /
  share_plus。直接加进 dependencies 即可，flutter 会为 ohos 平台注册它们。
- **app-facing**（只有 `platforms: ohos: {package, pluginClass}`，没有 implements）：
  file_picker / package_info_plus / app_links / flutter_secure_storage /
  flutter_native_splash。**不用改主包** —— 原生侧接管同名 MethodChannel 即可
  （file_picker 是 `miguelruivo.flutter.plugins.filepicker`，
  package_info_plus 是 `dev.fluttercommunity.plus/package_info`，
  app_links 是 `com.llfbandit.app_links/messages`，
  flutter_secure_storage 是 `plugins.it_nomads.com/flutter_secure_storage`）。
- **例外：file_picker 的 Dart 侧是 `late` 单例且没有默认值**，
  ohos 的 Dart registrant 不会注册它 → `FilePicker.platform` 抛
  LateInitializationError。已在 `lib/bootstrap.dart` 里对 ohos 手动
  `FilePicker.platform = FilePickerIO();`（FilePickerIO 用的是同一个 channel）。
  其余三个 app-facing 包的 platform interface 都有 MethodChannel 默认实现，不用管。

### 踩坑（pub 版本约束冲突）
- `flutter_secure_storage_ohos` 1.0.0 要 interface ^1.0.1 → override 到 ^2.1.1；
  但这会让 `flutter_secure_storage_windows` 升到 4.2.2（要 win32 6.x，
  HLOCAL 在 win32 6 里改名）→ 还得把 windows 实现钉在 4.1.0。
- `file_picker_ohos` 1.0.1 锁 win32 ^4.1.3 → override win32 到 ^5.12.0
  （它只在 lib/src/windows/ 用 win32，ohos 不编译）。
- `share_plus_ohos` 1.0.0 要 share_plus_platform_interface ^7.0.0 →
  share_plus 得升到 13.x（10.x 是 interface 5.x），API 变成
  `SharePlus.instance.share(ShareParams(files: [...]))`。
- `file_picker_ohos` 会传递引入 `image_picker`（app 不用，但会多一个 iOS pod：
  `image_picker_ios`），**ios/macos 的 Podfile.lock 需要重新生成**
  （`pod install`，要联网）。macOS 那边的 `file_selector_macos` 是 file_picker 8.3.7
  自带的，之前就没进已提交的 Podfile.lock，属于既有的陈旧。

### 本机环境限制
- **github.com / raw.githubusercontent.com 在本机不可达**（curl 返回 000，
  `git clone` 报 "Failed to connect to server"）→ `pod install` 必失败，
  **macOS/iOS 构建在本机无法验证**（macos/Pods 是空的，build/macos 下也从没有
  产出过 .app，说明这是既有状态，不是本次改动引入的）。
  ohos 构建不依赖 pod，可以正常验证。
